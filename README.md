# C-EMS 발표자료 제작 

이 리포지토리는 2026 HUSS Social AI Lab 경진대회 발표 자료 준비를 위한 공간입니다.

## 1. 프로젝트 핵심 방향
- 학교 에너지 절감 문제를 공공문제로 정의한다.
- 기존 시설관리자 중심 EMS의 한계를 지적한다.
- 실제 사용자인 학생·교직원이 참여할 수 있는 구조를 제안한다.
- C-EMS를 Competition-EMS로 확장한다.

## 2. 현재 발표 흐름 상태
- 최종 발표 흐름은 아직 확정되지 않았다.
- 현재는 문제의식, 심사기준, 시스템 구조를 바탕으로 흐름을 조정 중이다.
- 각 슬라이드는 추후 수정 가능성을 고려해 제작한다.

## 3. 임시 발표 논리
1. 왜 학교가 전기를 줄여야 하는가
2. 기존 관리는 왜 부족한가
3. 왜 학생·교직원의 참여 구조가 필요한가
4. 단순 절감이 아니라 공정한 기준이 왜 필요한가
5. Competition-EMS는 무엇인가
6. 시설팀과 구성원에게 각각 어떤 화면을 제공하는가
7. 예측·원인분석·게이미피케이션이 어떻게 연결되는가
8. 실제 수요기관과 어떻게 연결되어 실현 가능한가

## 4. 심사기준 우선순위
발표는 아래 심사기준에 맞춰 조정한다.

### 문제발굴 40점
- 적절성: 공공문제로서 적합한가
- 도전성: 해결할 가치가 크고 도전적인가
- 활용성: 해결 시 실제 활용 가능성이 높은가

### 문제해결 60점
- 독창성: 기존 방식과 다른 해결 방법인가
- 우수성: 해결 내용이 구체적이고 완성도가 높은가
- 실현 가능성: 수요기관과 연결된 실행 계획이 있는가

## 5. 디자인 방향
- 기술 발표 느낌은 유지하되, 너무 딱딱하지 않게 구성한다.
- 데이터, 에너지, 캠퍼스, 경쟁, 참여의 이미지를 함께 사용한다.
- 블랙, 딥네이비, 화이트를 기본으로 사용한다.
- 포인트 컬러는 블루, 민트, 라임, 전기빛 옐로우를 절제해서 사용한다.
- 한 슬라이드에는 하나의 메시지만 강하게 보여준다.

## 6. 금지 방향
- 학생들이 무지해서 전기를 안 줄인다는 식의 표현 금지
- 학교가 무조건 낭비하고 있다는 표현 금지
- 단순 전기요금 절약 프로젝트처럼 보이는 구성 금지
- 기능 나열식 발표 금지
- 예쁜 화면만 있고 문제의식이 약한 발표 금지

## 7. 최종적으로 남겨야 할 인상
이 발표는 단순한 에너지 절감 시스템 소개가 아니다.

핵심 메시지는 다음과 같다.

> 학교 에너지 절감의 문제는  
> 전기를 몰라서가 아니라,  
> 함께 참여할 수 있는 구조가 없었다는 점이다.

우리는 그 구조를 Competition-EMS로 제안한다.

## 폴더 구조

- README.md : 전체 프로젝트 설명 및 작업 규칙
- docs/ : 슬라이드별 기획 문서
  - slide1.md
  - slide2.md
  - slide3.md
- src/ : 실제 HTML/CSS/JS 슬라이드 파일
- assets/ : 이미지, 아이콘, 영상, 로고 등 발표자료 리소스
- output/ : 최종 결과물 저장 폴더

## 구현지시
- 제작 비율은 파워포인트 슬라이드 크기(16:9)로 제작한다.

## 작업 규칙

Antigravity는 작업 중 생성되는 파일을 역할에 맞는 폴더에 자동으로 정리한다.

- 슬라이드 기획 문서는 docs 폴더에 저장한다.
- 이미지, 아이콘, 배경 등 리소스 파일은 assets 폴더에 저장한다.
- HTML, CSS, JS 파일은 src 폴더에 저장한다.
- 최종 제출용 결과물은 output 폴더에 저장한다.
- 임시 파일이나 테스트 파일은 작업 완료 후 정리한다.
- 파일명은 slide1, slide2처럼 순서가 드러나게 작성한다.

## 디자인 및 구현 규칙

- 한 슬라이드에는 하나의 핵심 메시지만 담는다.
- 텍스트를 과하게 많이 넣지 않는다.
- 발표자가 말로 설명할 수 있도록 화면은 간결하게 구성한다.
- 색상은 블랙, 딥네이비, 화이트를 기본으로 사용한다.
- 포인트 컬러는 블루, 민트, 라임 계열을 사용한다.
- 애니메이션은 발표 흐름을 돕는 수준으로만 사용한다.
- 불필요하게 무거운 효과나 렉이 발생하는 효과는 피한다.

## 수정 규칙

- 기존 파일을 수정할 때는 전체 구조를 임의로 바꾸지 않는다.
- 사용자가 요청한 부분만 우선 수정한다.
- 큰 구조 변경이 필요할 경우, 먼저 이유를 설명하고 제안한다.
- 기존 디자인 톤을 유지하면서 개선한다.
- 사용자가 작성한 문구는 임의로 삭제하지 않는다.

## Antigravity 작업 지시사항

- 작업 전 README를 먼저 읽고 전체 방향을 파악한다.
- 새 파일을 만들 때는 반드시 역할에 맞는 폴더에 저장한다.
- 작업 후 변경된 파일과 변경 내용을 간단히 정리한다.
- 불필요한 파일은 만들지 않는다.
- 테스트 파일은 작업이 끝나면 삭제하거나 temp 폴더에 정리한다.
- 사용자가 요청하지 않은 대규모 구조 변경은 하지 않는다.
- 발표자료의 흐름, 디자인 톤, 핵심 메시지는 README 기준을 따른다.
